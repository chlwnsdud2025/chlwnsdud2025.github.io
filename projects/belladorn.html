PROJECT OVERVIEW

직업 전환과 스킬 강화로 성장하는 액션 RPG를 만들자

Belladorn은 한림대학교 캡스톤디자인(졸업 프로젝트)으로 3인이 10주 동안 만든 쿼터뷰 액션 RPG입니다. Unity 기초 수업으로 게임 개발을 시작한 뒤 만든 프로젝트로, 저는 플레이어가 성장하는 모든 경로 — 직업, 스킬, 장비, 퀘스트 — 와 그것을 보여 주는 UI를 맡았습니다.

기능이 많은 만큼 “데이터만 추가하면 늘어나는 구조”를 목표로 했습니다. 직업 · 스킬 · 강화 · 아이템 · 퀘스트 · 조건을 모두 ScriptableObject로 정의하고, 판정 · 스탯 변경 · 진행도 갱신은 각각 하나의 경로로 모았습니다.

내가 맡은 일

  • 직업 시스템 — JobType 하나로 모델 · 애니메이터 · 스킬 세트 · 스탯을 데이터로 교체
  • 스킬 실행 · 히트박스 — 애니메이션 이벤트 타이밍 + Shape / 다단 히트 / 투사체 히트박스 프리팹
  • 스킬 강화 · QWER 장착 — 포인트 레벨업 · 분기 강화 · 같은 계열 중복 장착 방지
  • 인벤토리 · 장비 · 퀵슬롯 — 직업 제한 장비 · StatModifier 단일 경로 · 드래그 앤 드롭
  • 퀘스트 · 대화 — 조건 SO 조합 · 이벤트 기반 진행 · 연계 퀘스트
  • 씬 흐름 · 캐릭터 선택 — 4개 씬 · 매니저 유지 · 직업 선택 화면

THE GAME

한 생명을 대가로 불러낸, 과거의 영웅

봉인의 열쇠가 시간의 문을 열고, 한 생명을 대가로 과거의 영웅을 현재로 불러냅니다. 플레이어는 계승할 영웅(직업)을 골라 숲과 유적을 지나며 퀘스트를 수행하고, 챕터 1의 보스에 도전합니다.

진행 흐름

메인 메뉴→튜토리얼→유물 컷신→영웅(직업) 선택→챕터 1 · NPC 퀘스트→보스전
HERO

영웅 계승

튜토리얼을 마치면 계승할 영웅을 고릅니다. 직업마다 모델 · 애니메이션 · 스킬 세트 · 기본 스탯이 모두 달라집니다.

SKILL

QWER 스킬 빌드

레벨업으로 얻은 포인트로 스킬 레벨을 올리고, 갈라지는 강화 스킬 중 하나를 골라 QWER 슬롯에 자유롭게 배치합니다.

GEAR

장비와 소비 아이템

직업에 맞는 장비를 7부위에 장착하고, 포션과 버프 아이템을 퀵슬롯에 등록해 전투 중 사용합니다.

QUEST

NPC와 퀘스트

숲의 NPC와 대화하며 처치 · 수집 · 아이템 사용 · 지점 도달 퀘스트를 이어 받고, 끝에서 챕터 보스를 만납니다.

ENGINEERING NOTES

구현 사례

01

직업 시스템 — JobType 하나로 모든 것을 교체

직업 변경은 JobType 하나만 넘기면 모델 · 애니메이터 · 스킬 세트 · 스탯이 데이터(ScriptableObject)로 한 번에 바뀝니다.

설계
  • 데이터 분리 — 직업별 JobResources(모델 프리팹 · Animator Controller · Avatar), JobSkillData(스킬 세트), JobStatusData(기본 스탯 · 레벨당 성장치). 직업 추가는 데이터 추가로 처리
  • 교체 순서 — 모델 → Animator · Avatar → 스킬 세트 → 상태 머신 Idle → 직업 스탯 → UI 갱신
  • 이벤트 알림 — 교체가 끝나면 한 프레임 뒤 OnJobChanged 발행 → 캐릭터 프리뷰 · 스킬 UI가 새 모델 기준으로 갱신
  • 씬 유지 — DontDestroyOnLoad 싱글턴, 씬이 로드되면 플레이어를 다시 찾아 현재 직업을 재적용
직업 하나로 모델 · 애니메이터 · 스킬 · 스탯을 함께 교체 (발췌) JobManager.cs
public void ChangeJob(JobType newJob)
{
    currentJob = newJob;
    var res = jobResourcesDict[newJob];

    if (currentModel != null) Destroy(currentModel);
    currentModel = Instantiate(res.modelPrefab, modelParent);            // 1. 모델

    playerAnimator.runtimeAnimatorController = res.animatorController;   // 2. 애니메이터
    playerAnimator.avatar = res.avatar;

    if (GetSkillData(newJob) is JobSkillData skillData)
        playerSkill.LoadSkillsFromData(skillData);                       // 3. 스킬 세트

    stateMachine.ChangeState(PlayerStateMachine.PlayerState.Idle);
    playerStatus.ApplyJobStats(GetStatData(newJob));                     // 4. 직업 스탯
    playerStatus.UpdateAllUI();

    StartCoroutine(InvokeJobChangedDelayed(newJob));                     // 5. 한 프레임 뒤 OnJobChanged
}

02

스킬 실행 · 히트박스 — 타이밍은 애니메이션에, 범위는 프리팹에

판정 타이밍은 애니메이션 이벤트에, 판정 범위 · 횟수 · 형태는 히트박스 프리팹에 맡겨 스킬마다 판정 코드를 새로 짜지 않도록 구성했습니다.

설계내용
입력 → 실행QWER 슬롯 키로 장착된 스킬을 조회 → 이동 정지 · 마우스 방향 회전 → 스킬 애니메이션 재생 (Root Motion)
타이밍모션의 타격 프레임에 넣은 Animation Event가 ActivateHitbox · SpawnEffect · PlaySkillSound를 호출
범위히트박스 프리팹마다 Sphere · Box · Cone(각도 · 거리) 중 선택
다단 히트startDelay · repeatCount · repeatInterval만으로 단타 · 연타 구성
투사체속도로 날아가다 충돌하면 2차 폭발 히트박스(secondaryHitboxPrefab)를 이어서 생성
위치 기준시전자를 따라가는 판정 / 시전 순간의 마우스 지점에 고정되는 판정
피아 구분PlayerHitbox · EnemyHitbox 태그와 레이어 마스크로 대상을 거른 뒤 CharacterStatus.TakeDamage() 호출 — 공격 판정과 피격 처리를 분리
시작 지연 · 반복 횟수 · 간격만으로 단타 / 다단 히트 구성 (발췌) HitBox.cs
private IEnumerator HandleHitbox()
{
    yield return new WaitForSeconds(startDelay);

    for (int i = 0; i < repeatCount; i++)
    {
        ApplyDamage();                                    // Shape별 Overlap 판정 → TakeDamage
        yield return new WaitForSeconds(0.1f);

        if (i < repeatCount - 1)
            yield return new WaitForSeconds(repeatInterval);
    }

    yield return new WaitForSeconds(duration);
    Destroy(gameObject);
}

03

스킬 강화와 QWER 장착 — 갈라지는 강화, 겹치지 않는 슬롯

스킬 포인트로 레벨을 올리고, 원본에서 갈라지는 강화 스킬을 골라 QWER에 자유롭게 등록합니다. 원본과 강화 스킬은 같은 계열로 묶어 동시에 장착되지 않게 막았습니다.

설계
  • 스킬 포인트 — 레벨업 시 획득(최대 8) · 레벨업 비용 = 다음 레벨(Lv.1 → 2는 2포인트) · 레벨을 내리면 환불 · 최대 Lv.5
  • 분기 강화 — 원본 스킬마다 SkillUpgradeData에 강화 옵션(최대 3개), 강화 스킬은 originalSkill로 원본과 연결해 레벨 동기화
  • 드래그 앤 드롭 장착 — 스킬 창에서 QWER 슬롯으로 끌어 등록
  • 강화 즉시 반영 — 이미 장착된 스킬을 강화하면 같은 슬롯에 강화 버전이 바로 들어감
원본 스킬과 강화 스킬은 같은 계열 — 중복 장착 방지 SkillEquipManager.cs
public void EquipSkill(string key, SkillInfo skill)
{
    foreach (var pair in equippedSkills)
    {
        if (pair.Key == key) continue;                    // 자기 슬롯은 제외
        bool isSameLine =
            pair.Value == skill ||
            pair.Value.originalSkill == skill ||
            skill.originalSkill == pair.Value;
        if (isSameLine) return;
    }
    equippedSkills[key] = skill;
    skill.skillKey = key;
}

04

인벤토리 · 장비 · 퀵슬롯 — 스탯이 바뀌는 길은 하나

장비와 소비 아이템 버프가 같은 스탯 변경 경로(StatModifier)를 쓰게 해서, 적용과 해제가 항상 대칭이 되도록 구성했습니다.

설계내용
아이템 데이터ItemData(SO)를 상속해 EquipmentData(7부위 · 착용 가능 직업 · StatModifier 목록), ConsumableData(체력 · 마나 회복 · 공격 / 방어 버프 · 지속 회복)로 확장
인벤토리48칸 · 같은 아이템은 최대 스택까지 합치고 남은 수량은 빈 칸에 · 획득 시 퀘스트 CollectItem 조건 갱신
장비착용 가능 직업 확인 → 같은 부위 기존 장비 해제 → StatModifier 적용 / 해제 시 같은 값을 음수로 되돌림
스탯 경로 통일장비 · 소비 버프 모두 StatusEffectApplier로 스탯을 바꿔, 어디서 바꿨든 같은 방식으로 되돌릴 수 있음
퀵슬롯1 ~ 4 키로 소비 아이템 사용 → 수량 차감 → 퀘스트 UseItem 조건 갱신
UI인벤토리 ↔ 장비 ↔ 퀵슬롯 드래그 앤 드롭 · 툴팁 · 창 헤더 드래그 이동 · 현재 직업 모델을 비추는 캐릭터 프리뷰(RenderTexture)
장착은 StatModifier 적용, 해제는 같은 값을 음수로 (발췌) EquipmentManager.cs
public void EquipItem(EquipmentData equipment)
{
    if (!equipment.allowedJobs.Contains(JobManager.Instance.GetCurrentJob())) return;   // 직업 제한

    if (equippedItems.TryGetValue(equipment.equipmentType, out var oldEquip))
        UnequipItem(oldEquip);                                                          // 같은 부위 교체

    equippedItems[equipment.equipmentType] = equipment;
    var modifiers = equipment.GetAllStatModifiers();
    appliedModifiers[equipment.equipmentType] = new List<StatModifier>(modifiers);
    StatusEffectApplier.ApplyStatModifiers(playerStatus, modifiers);
}

public void UnequipItem(EquipmentData item)
{
    var negativeMods = new List<StatModifier>();
    foreach (var mod in appliedModifiers[item.equipmentType])
        negativeMods.Add(new StatModifier(mod.type, -mod.value, mod.isFlat));
    StatusEffectApplier.ApplyStatModifiers(playerStatus, negativeMods);
    // ...
}

05

퀘스트 · 대화 — 시스템은 “무슨 일이 일어났는지”만 알린다

퀘스트는 조건 ScriptableObject를 조합한 에셋으로 만들고, 적 사망 · 아이템 획득 같은 각 시스템은 이벤트 종류와 ID만 넘겨 진행도를 올립니다.

설계
  • 조건 조합 — 추상 QuestCondition(SO)을 상속한 KillEnemy · CollectItem · UseItem · TalkToNPC · ReachArea 조건을 퀘스트마다 섞어서 구성
  • 이벤트 기반 진행 — 각 시스템은 UpdateCondition(type, id)만 호출 → 진행 중인 퀘스트의 맞는 조건만 갱신
  • 상태 분리 — 정의(QuestData)와 런타임 진행(PlayerQuestProgress) 분리 · InProgress → Completed → Rewarded
연결
  • 연계 퀘스트 — 보상을 받으면 nextQuestID로 다음 퀘스트를 불러와 자동 수락 → 메인 스토리를 에셋 연결로 구성
  • 영역 조건 — 수락 시 목표 지점에 트리거를 생성하고, 도달하면 제거
  • UI 갱신 — OnQuestUpdated 이벤트로 HUD · 퀘스트 목록 · 상세 창 갱신, NPC 대화와 수락 내레이션 출력
시스템은 type · id만 넘기고, 조건 매칭은 QuestManager가 (발췌) QuestManager.cs
public void UpdateCondition(string type, string identifier, int amount = 1)
{
    foreach (var progress in activeQuests)
    {
        if (progress.state != QuestState.InProgress) continue;

        for (int i = 0; i < progress.questData.conditions.Count; i++)
        {
            var condition = progress.questData.conditions[i];
            if (condition is KillEnemyCondition killCond && type == "KillEnemy" && killCond.targetEnemyTag == identifier)
                progress.IncrementProgress(i, amount);
            else if (condition is ReachAreaCondition areaCond && type == "ReachArea" && areaCond.areaID == identifier)
            {
                progress.IncrementProgress(i, amount);
                QuestAreaTriggerSpawner.Instance?.RemoveTrigger(identifier);
            }
            // CollectItem · TalkToNPC · UseItem도 같은 방식
        }

        if (progress.IsAllConditionsMet() && progress.state != QuestState.Completed)
            progress.state = QuestState.Completed;

        OnQuestUpdated?.Invoke(progress);
    }
}

06

씬 흐름 · 캐릭터 선택 — 씬이 바뀌어도 끊기지 않게

메인 메뉴 → 튜토리얼 → 캐릭터 선택 → 챕터 1로 이어지는 씬을 나누고, 씬이 바뀌어도 직업 · 진행 데이터가 끊기지 않도록 구성했습니다.

설계
  • 컷신 전환 — 튜토리얼 마지막 퀘스트를 완료하고 유물과의 대화가 끝나면 화면을 페이드아웃하고 내레이션을 순서대로 띄운 뒤, [G] 입력 시 캐릭터 선택 씬으로 이동
  • 캐릭터 선택 — 직업마다 카메라 포인트로 이동하며 직업 설명 · 난이도(1 ~ 5) · 추천 대상 · 플레이 스타일 표시 → 확정 시 선택 직업을 JobManager에 저장하고 게임 씬 로드
  • 데이터 유지 — 직업 정보를 가진 매니저를 씬 사이에서 유지하고, 새 씬이 로드되면 플레이어와 UI 참조를 다시 연결
