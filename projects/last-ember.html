PROJECT OVERVIEW

소울라이크의 정밀한 조작감을 재현해 보자

소울라이크 전투의 손맛은 “언제 다음 공격이 이어지고, 언제 구르기로 끊을 수 있고, 언제 무적인가”가 모션의 특정 순간에 정확히 맞물리는 데서 나옵니다. Last Ember는 다크소울 시리즈를 참고해, 이 타이밍들을 애니메이션 진행도(normalizedTime) 기준으로 제어하는 데 집중한 1인 개발 프로젝트입니다.

학원의 첫 개인 프로젝트로, 1인 개발 프로세스 숙달 · FSM 구조 이해 · FBX 리소스와 애니메이션 활용을 목표로 했습니다. 이 과정에서 FSM과 ScriptableObject로 상태와 데이터를 분리하는 법을 익혔고, 이후 팀 프로젝트의 데이터 설계로 이어졌습니다.

핵심 구현

  • 애니메이션 진행도 동기화 — normalizedTime으로 판정 · 콤보 · 캔슬 · 무적 구간 제어, 타임라인 커스텀 인스펙터
  • FSM 기반 상태 관리 — Controller → StateMachine → BaseState 공통 골격, FSM마다 전환 기준만 다르게
  • 보스 전용 AI — 거리 · 쿨타임 · 페이즈 필터 → 가중치 룰렛 → 허브 구조의 Decision State
  • 데이터 주도 설계 — ScriptableObject로 밸런스 값과 로직 분리, 무기 교체 = SO 교체

THE GAME

마지막 불씨를 지키는 소울라이크

플레이어는 화톳불을 거점 삼아 몬스터가 도사리는 지역을 탐험합니다. 무기마다 다른 연속 공격과 구르기 · 대시로 적의 공격을 피하고 받아치며, 아이템과 레벨업으로 성장해 보스 Skeleton Guardian에게 도전합니다.

COMBAT

전투

무기별 연속 공격 · 선입력 · 공격 캔슬, 무적 구간이 있는 구르기와 대시, 타겟 락온으로 1:1 전투에 집중할 수 있습니다.

ENEMY

적과 보스

일반 몬스터는 감지 범위와 시야각으로 플레이어를 찾아 추적합니다. 보스는 가중치 랜덤으로 패턴을 고르고, 체력 50%에서 2페이즈로 전환됩니다.

GROWTH

성장과 거점

아이템을 얻어 무기 · 방어구 · 장신구 · 소모품을 장착하고, 화톳불에서 휴식하며 스탯을 분배해 레벨업합니다.

DEATH

죽음과 부활

사망하면 마지막으로 쉰 화톳불에서 부활하고 월드가 리셋됩니다. 소울라이크의 반복 도전 구조를 따랐습니다.

ENGINEERING NOTES

구현 사례

01

애니메이션 진행도로 공격 판정과 콤보 구간을 제어

매 프레임 현재 클립의 normalizedTime(0~1)을 읽어, ScriptableObject에 정의한 구간과 비교해 판정 · 콤보 · 캔슬 · 무적을 켜고 끕니다. 구간 값은 커스텀 인스펙터의 타임라인에서 모션을 보며 조절합니다.

문제

고정된 시간(초)으로 판정이나 콤보 타이밍을 정하면, 무기마다 다른 모션 길이나 재생 속도가 바뀔 때마다 값을 다시 맞춰야 합니다. 또 애니메이션이 다음 상태로 섞여 넘어가는 동안에는 “지금 어느 모션의 몇 %인지”가 흔들려 판정이 튈 수 있었습니다.

설계
  • 매 프레임 진행도 조회 — Update에서 현재 클립의 normalizedTime을 0~1로 직접 읽음
  • SO의 구간 값과 비교 — 판정 · 콤보 · Cancel · 무적 구간을 진행도 범위로 On/Off
  • 전환 중에는 판정 보류 — IsInTransition이 아니고 State 해시가 맞을 때만 구간 적용
진행도를 SO에 정의된 구간과 비교 AttackState.cs
AnimatorStateInfo stateInfo = player.animator.GetCurrentAnimatorStateInfo(0);
float progress = stateInfo.normalizedTime;                    // 0 ~ 1
AttackData currentAttackData = player.currentWeapon.comboAttacks[comboIndex];

bool isPlayingAttack = stateInfo.shortNameHash == expectedHash;
if (isPlayingAttack && !player.animator.IsInTransition(0))   // 전환 중에는 보류
{
    player.canCombo      = progress >= currentAttackData.comboWindowStart
                        && progress <= currentAttackData.comboWindowEnd;
    player.canNextAttack = progress >= currentAttackData.comboTransitionPoint;
    player.canCancel     = progress >= currentAttackData.cancelWindowStart;
}
결과
  • 무기 · 모션이 바뀌어도 구간은 “모션의 몇 %”로 정의되므로 State 코드는 그대로
  • 모션 전환 중 판정이 튀는 문제 없이, 같은 모션에서만 구간이 적용됨
  • 공격 · 구르기 · 보스 패턴 SO 모두 같은 방식으로 구간을 정의
커스텀 인스펙터

공격 · 구르기 · 보스 패턴 SO에 구간 타임라인, 모션 미리보기, 개별 값 조절 필드를 한 화면에 배치했습니다. 숫자만 보고 맞추던 구간을 해당 시점의 실제 포즈를 확인하며 조절할 수 있습니다.

02

세 FSM이 공유하는 골격, 다른 전환 기준

Controller가 State를 만들고 StateMachine이 현재 State 하나만 실행하는 공통 골격 위에서, Player · Enemy · Boss가 “무엇이 다음 상태를 결정하는가”만 다르게 설계했습니다.

Controller · MonoBehaviour→StateMachine · 순수 C#→BaseState · Enter / Update / Exit
공통 구조
  • Controller — Awake에서 모든 State를 한 번만 생성하고, 매 프레임 실행은 StateMachine에 위임
  • StateMachine — 현재 State 하나만 실행하고, 교체 시 Exit → Enter 순서를 보장
  • BaseState — Enter · Update · Exit 중 필요한 메서드만 override
FSM을 적용한 이유
  • 겹치면 안 되는 행동 분리 — 공격 · 구르기 · 피격이 겹치지 않도록 한 번에 State 하나만 실행
  • 같은 입력, 상태별로 다른 반응 — 공격 입력도 Idle은 공격 시작, Attack은 콤보 예약, Hit · Dead는 무시
  • 적은 확장 비용 — 새 행동은 State 클래스 하나만 추가, 기존 State 코드는 수정하지 않음
FSM전환 기준설계 포인트
Player공격 · 구르기 · 포션 · 상호작용 입력 → 현재 State가 해석Controller는 입력을 현재 State에 전달만 함. 이동은 매 프레임 폴링, 공격 · 구르기는 normalizedTime으로 스스로 종료. 판정 · 콤보 · 무적 구간은 SO에 두어 무기를 바꿔도 State 코드는 그대로
Enemy플레이어와의 거리 (3m 근접 · 10m 감지 · 15m 해제)반경 · 시야각 · 장애물 Raycast를 모두 통과해야 Chase. 공격이 끝나면 항상 Strafe로 빠져 쿨타임 동안 간격 유지. 패턴 SO마다 AttackState를 만들고 사거리 · 쿨타임을 통과한 패턴 중 가중치로 선택
Boss거리 · 쿨타임 · 페이즈 필터 → 가중치 룰렛모든 행동 State는 끝나면 Decision으로 복귀 (State끼리 직접 전환 없음) — 아래 03에서 자세히

03

모든 행동이 Decision을 거치는 보스 AI

보스의 다음 행동은 Decision State에서만 결정됩니다. 조건을 통과한 패턴 중 가중치 랜덤으로 하나를 고르고, 행동이 끝나면 다시 Decision으로 돌아오는 허브 구조입니다.

  1. 후보 필터 — 거리(min ~ max) · 쿨타임 · 페이즈 중 하나라도 불만족하면 제외. 기준값은 패턴 SO에서 읽음
  2. 가중치 룰렛 — 남은 후보를 baseWeight 비율로 룰렛을 돌려 1개 추출
  3. 전이 — 공격 패턴이면 공격 SO를 Attack State에 주입하고, 패턴의 StateType으로 등록된 State로 전이
  4. 복귀 루프 — 각 State의 행동이 끝나면 Decision State로 복귀
설계 포인트
  • 한 프레임 안에 판단 — Enter()에서 필터 → 룰렛 → 전이까지 끝내 Decision에 머무르지 않음
  • 행동 목록은 인스펙터 데이터 — BossActionOption 리스트와 공격 SO만으로 보스의 패턴 구성을 정의
  • 페이즈 전환 — 체력 50% 이하에서 PhaseChange State를 거쳐 requiredPhase가 2인 패턴이 후보에 추가됨
결과

State끼리 직접 전환하는 경로가 없어서, 패턴을 추가하거나 빼도 다른 State를 수정할 필요가 없습니다. 패턴의 등장 조건과 확률은 모두 인스펙터 데이터라 코드 수정 없이 보스의 성격을 조정할 수 있습니다.

후보 필터 → 가중치 룰렛 Humanoid_Boss_DecisionState.cs
foreach (var option in boss.availableActions)
{
    if (distanceToPlayer < option.minDistance || distanceToPlayer > option.maxDistance) continue;
    if (Time.time < option.lastUsedTime + option.cooldown) continue;
    if (option.stateType == BossStateType.Attack && option.attackData != null
        && option.attackData.requiredPhase > boss.currentPhase) continue;   // 페이즈 판단

    validOptions.Add(option);
    totalWeight += option.baseWeight;
}

int randomValue = Random.Range(0, totalWeight);
int cumulativeWeight = 0;
foreach (var option in validOptions)
{
    cumulativeWeight += option.baseWeight;
    if (randomValue < cumulativeWeight) { option.lastUsedTime = Time.time; return option; }
}

04

값은 SO, 규칙은 State — 데이터 주도 설계

ScriptableObject로 밸런스 값과 로직을 분리했습니다. 무기를 바꾸는 일은 State 코드를 바꾸는 일이 아니라 SO를 바꾸는 일이 됩니다.

무기 SO의 클립으로 애니메이터 덮어쓰기 PlayerController.cs
public void EquipWeapon(Attack_SO_Data newData)
{
    Attack_SO_Data targetData = newData != null ? newData : defaultUnarmedData;
    currentWeapon = targetData;

    for (int i = 0; i < targetData.comboAttacks.Length; i++)
        overrideController[$"Attack{i + 1}"] = targetData.comboAttacks[i].clip;

    if (targetData.idleClip != null)   overrideController["Idle"]   = targetData.idleClip;
    if (targetData.walkClip != null)   overrideController["Walk"]   = targetData.walkClip;
    if (targetData.runClip != null)    overrideController["Run"]    = targetData.runClip;
    if (targetData.sprintClip != null) overrideController["Sprint"] = targetData.sprintClip;
    ...
}
구분설계내용
패턴 · 모션 SO값은 SO, 규칙은 State판정 · 콤보 · Cancel 구간은 SO에 두고, State는 매 프레임 읽기만 함
무기 교체 = SO 교체장착 시 AnimatorOverrideController로 공격 · 이동 클립만 바꾸고 State 코드는 그대로
런타임 기록은 SO 밖에쿨타임 기록은 State · 행동 목록에 두어 같은 SO를 여러 개체가 공유
아이템 SO공통 필드는 ItemDataBaseID · 이름 · 아이콘 · 등급 · 가격을 공유하고, 무기 · 방어구 · 장신구 · 소모품별로 필요한 필드만 추가
원본과 소지 상태 분리SO는 공유 원본, 개수 · 강화 수치는 ItemInstance가 따로 보관
ID 기반 저장 대비저장 대상은 itemID뿐, SO 참조는 NonSerialized로 저장에서 제외

배운 점
