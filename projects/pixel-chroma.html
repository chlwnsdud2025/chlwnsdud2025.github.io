PROJECT OVERVIEW

네트워크 환경을 직접 구축하고, 출시까지

Pixel Chroma는 메챠카멜레온에서 영감을 받은 2D 도트 버전 숨바꼭질입니다. 도트 그래픽은 배경과 색을 정확히 맞추면 눈으로 찾기가 거의 불가능하다는 점을 핵심 재미로 삼았습니다.

4인 팀이 약 11주 동안 개발해 Steam에 출시했습니다. 저는 “전용 서버 없이 동작하는 멀티플레이”를 목표로 Steam 로비 기반 매칭, 플레이어 색칠과 사용자 제작 픽셀 닉네임의 동기화, 그리고 실제 플레이에서 발견된 네트워크 문제의 해결을 담당했습니다.

12인한 방의 최대 동시 플레이어
4→1입장 경로 4가지를 하나의 입장 콜백으로 통합
3초퀵 매칭이 검색 조건을 한 단계씩 완화하는 주기

내가 맡은 일

  • 매칭 시스템 — Steam Lobby와 Mirror를 역할별로 분리하고 빠른 매칭·코드 참가·공개 로비 검색·친구 초대를 하나의 흐름으로 통합
  • 매칭 품질 — 3초마다 조건을 완화하는 퀵 매칭, 유령방을 줄이는 로비 목록 갱신과 실패 복구
  • 색칠 동기화 — 폼별 마스크 1장 저장, 마스크 대신 입력만 전송, 늦은 입장 청크 동기화
  • 픽셀 닉네임 — 60×12 픽셀 닉네임 저장·업로드·재사용 구조
  • 트러블슈팅 — 서버 지연으로 정상 발사가 무시되던 문제 해결

THE GAME

배경과 같은 색이 되면, 보이지 않는다

크로마는 준비 시간 동안 팔레트에서 색을 골라 자기 캐릭터를 픽셀 단위로 칠해 배경에 녹아듭니다. 술래는 의심되는 곳마다 물총을 쏴서 숨은 크로마를 찾아냅니다. 단 한 발이라도 맞으면 즉시 검거됩니다.

CHROMA

칠해서 숨는 크로마

브러시 · 지우개 · 채우기로 캐릭터를 픽셀 단위로 칠합니다. 기본 모습 외에 버섯 · 별 · 큐브 · 원 폼으로 바꿔 가며 배경 속 사물처럼 숨을 수 있고, 폼마다 칠한 색이 따로 저장됩니다.

SEEKER

쏴서 찾는 술래

물총은 1.5초 쿨타임과 탄약 제한이 있어, 아무 곳이나 쏘기보다 배경과 어긋난 픽셀을 관찰해 의심 지점을 골라야 합니다.

BALANCE

엠보싱 외곽선

단색으로 완벽하게 칠해도 캐릭터 외곽선에 그림자와 하이라이트가 남아, 술래가 명암 경계를 단서로 쓸 수 있습니다.

MODE

기본 · 감염 모드

기본 모드는 술래가 제한 시간 안에 크로마 전원을 검거하면 승리합니다. 감염 모드에서는 잡힌 크로마가 술래로 전환됩니다.

한 판의 흐름

  1. 로비에 모이기 — 빠른 매칭, 방 코드, 공개 로비 검색, Steam 친구 초대 중 하나로 최대 12명이 한 방에 모입니다. 방장은 숨는 시간 · 찾는 시간 · 술래 수 · 맵 같은 방 옵션을 정합니다.
  2. 숨는 시간 (Hide Time) — 크로마는 색을 칠하고 폼을 바꿔 가며 숨을 자리를 찾습니다. 기본 120초입니다.
  3. 찾는 시간 (Seek Time) — 술래가 물총으로 크로마를 찾습니다. 옵션을 켜면 일정 간격(기본 40초)마다 살아 있는 크로마가 강제로 노출되고, 크로마의 도발과 물총 소리는 3D 사운드로 위치를 가늠하는 단서가 됩니다.
  4. 결과 확인 (Check Time) — 제한 시간 안에 전원 검거하면 술래 승리, 한 명이라도 끝까지 살아남으면 크로마 승리입니다.

ENGINEERING NOTES

구현 사례

01

Steam이 “만남”을, Mirror가 “통신”을 — 매칭 시스템

Steam 로비를 매칭 계층으로 두고, 네 가지 입장 경로를 하나의 LobbyManager로 통합했습니다. 두 계층은 호스트의 SteamID 하나로 연결됩니다.

문제

빠른 매칭, 방 코드 참가, 공개 로비 검색, 친구 초대가 각자 다른 방식으로 방을 찾지만, 결국 같은 방 정보와 같은 접속 절차를 공유해야 했습니다. 경로마다 접속 코드를 따로 두면 실패 처리와 안내도 네 벌이 됩니다.

설계
  • 모든 경로가 SteamMatchmaking.JoinLobby → OnLobbyEnteredCallback 하나로 합류
  • 콜백에서 로비 메타데이터의 HostAddress(호스트 SteamID)를 읽어 Mirror 클라이언트 시작
  • 실패 사유는 LobbyFailureReason enum 하나로 모아 각 입장 UI가 다국어로 안내

두 계층의 역할

계층담당하는 일
만남 계층Steam Lobby · Steamworks.NET방 생성 · 공개 설정 · 인원 제한, 메타데이터로 검색 · 필터. Steam 서버가 조건에 맞는 방만 검색자에게 돌려줌
통신 계층Mirror · FizzySteamworksSyncVar · Command · ClientRpc로 게임 상태 동기화. IP 대신 SteamID로 접속하고, Steam 릴레이로 NAT 통과 · IP 비노출

호스트가 서버를 겸하는 Listen Server 구조라 전용 게임 서버 없이 동작합니다.

검색과 방 정보 표시는 로비 메타데이터 하나로 처리합니다.

// Steam 로비 입장이 끝나면 HostAddress(호스트 SteamID)로 Mirror 클라이언트를 시작
private void OnLobbyEnteredCallback(LobbyEnter_t result)
{
    bool success = result.m_EChatRoomEnterResponse == (uint)EChatRoomEnterResponse.k_EChatRoomEnterResponseSuccess;
    if (!success)
    {
        OnLobbyFailed?.Invoke(LobbyFailureReason.JoinFailed);   // 실패 사유 enum으로 UI에 전달
        return;
    }

    CurrentLobbyId = new CSteamID(result.m_ulSteamIDLobby);
    if (IsHost) return;

    CurrentRoomCode = SteamMatchmaking.GetLobbyData(CurrentLobbyId, CodeKey);
    string hostAddress = SteamMatchmaking.GetLobbyData(CurrentLobbyId, HostAddressKey);

    _waitingForConnection = true;
    NetworkManager.singleton.networkAddress = hostAddress;      // IP가 아닌 SteamID
    NetworkManager.singleton.StartClient();
}

왜 Steam + Mirror인가

EOS, Unity Relay + NGO, Photon 같은 대안 중에서 Steam 단독 출시라는 기획에 맞춰 비용과 Steam 호환성 면에서 가장 유리한 조합을 골랐습니다.

선택 이유
  • Steam 호환성 — SteamID가 곧 접속 주소라 별도 계정 체계 없이 로비 · 초대 · 접속을 하나로 처리
  • 비용 0 — 호스트가 서버를 겸하고 Steam 릴레이는 무료라, 동시 접속자가 늘어도 서버 · 중계 비용이 없음

  • Mirror는 전송 계층이 분리돼 있어 크로스플랫폼이 필요해지면 Transport만 EOS로 교체 (동기화 코드 유지)
  • Steam 전용이라는 제약은 Steam 단독 출시 기획이라 영향 없음

private static CSteamID PickBestLobby(uint count)
{
    CSteamID bestLobby = CSteamID.Nil;
    int bestMemberCount = -1;
    for (int i = 0; i < (int)count; i++)
    {
        CSteamID lobbyId = SteamMatchmaking.GetLobbyByIndex(i);
        int memberCount = SteamMatchmaking.GetNumLobbyMembers(lobbyId);
        if (memberCount >= SteamMatchmaking.GetLobbyMemberLimit(lobbyId)) continue;   // 꽉 찬 방 제외

        string mapId = SteamMatchmaking.GetLobbyData(lobbyId, LobbyManager.MapIdKey);
        if (WorkshopMapId.TryGetFileId(mapId, out ulong fileId)
            && !WorkshopSubscriptionService.IsInstalled(fileId)) continue;          // 미설치 창작마당 맵 제외

        if (memberCount > bestMemberCount) { bestMemberCount = memberCount; bestLobby = lobbyId; }
    }
    return bestLobby;
}

03

칠한 색은 마스크 1장에, 동기화는 입력만

칠한 색은 폼별 마스크 1장에 저장하고, 다른 클라이언트에는 마스크가 아니라 입력만 보내 각자 같은 연산으로 재현합니다.

문제

크로마는 여러 폼과 프레임 애니메이션을 가집니다. 프레임마다 텍스처를 복사해 칠하면 메모리가 늘고, 칠할 때마다 텍스처를 통째로 보내면 전송량이 커집니다. 게다가 폼을 바꿨다 돌아오거나 게임 도중 새 플레이어가 들어와도 칠한 모습이 똑같아야 했습니다.

SHARED PAINT MASK
Original Sprite프레임 애니메이션
+
Color32 Mask폼별 색칠 데이터
→
Composite모든 프레임에 같은 색

원본 스프라이트는 그대로 두고, 마스크 1장을 모든 프레임이 공유

설계내용
폼별 페인트 마스크 1장칠한 색은 원본 스프라이트와 분리된 마스크(Color32[])에 칸 단위로 기록. 모든 애니메이션 프레임이 같은 칸 좌표를 공유해 폼마다 1장으로 처리
입력만 전송브러시 · 지우개는 좌표 · 색 · 크기, 채우기는 시작 좌표 · 색만 Command → ClientRpc로 전송. 각 클라이언트가 같은 연산을 재실행해 동일한 마스크를 재현
늦은 입장 동기화새로 들어온 클라이언트에게만 호스트가 모든 폼의 칠해진 칸을 모아 전송. 메시지 크기 상한에 맞춰 1,000칸씩 나눠 TargetRpc로 전달
늦게 들어온 클라이언트에게 칠해진 칸만 1,000칸 단위로 전송 PlayerPaintCanvas.cs
for (int i = 0; i < pixels.Length; i++)
{
    if (pixels[i].a == 0) continue;          // 칠하지 않은 칸은 건너뜀
    idxBuf.Add(i);
    colBuf.Add(pixels[i]);

    if (idxBuf.Count == RelayMaxCells)       // 1000칸 단위로 분할
    {
        TargetLoadSnapshot(conn, form.formType, firstChunk, idxBuf.ToArray(), colBuf.ToArray());
        firstChunk = false;
        idxBuf.Clear();
        colBuf.Clear();
    }
}
결과
  • 저장 — 프레임별 텍스처 복사 없이 폼마다 마스크 1장만 유지
  • 전송 — 한 번 칠할 때 좌표 · 색 · 크기만 보내 수십 바이트로 동기화
  • 복원 — 늦게 들어오거나 폼을 바꿨다 돌아와도 칠한 모습 그대로

04

사용자 제작 픽셀 닉네임 — 접속당 한 번만 올리기

플레이어가 60×12 픽셀로 직접 그린 닉네임을 로컬에 저장하고, 접속 시 한 번만 서버에 올려 모든 클라이언트가 재사용합니다.

문제

닉네임이 텍스트가 아니라 이미지라서, 씬이 바뀌거나 술래로 전환돼 플레이어 오브젝트가 새로 만들어질 때마다 다시 보내면 전송량이 빠르게 늘어납니다. 닉네임을 보여 주는 UI(머리 위 · 채팅 · 킬로그 · 점수판 · 인디케이터)도 여러 곳이었습니다.

설계
  • 편집용 / 전송용 키 분리 — 프리셋 3개는 편집용, 메인 키 1개는 전송용. 어떤 프리셋을 편집해도 전송은 메인 키 하나만 읽음
  • 접속당 1회 업로드 — 서버가 connId별 명부(NicknameRegistry)에 보관하고 SyncVar로 배포. 씬 · 술래 전환 시엔 명부의 PNG를 새 오브젝트에 바로 입힘
  • 받은 데이터 재사용 — 채팅 · 킬로그 · 점수판 · 인디케이터는 netId로 플레이어를 찾아 같은 PNG를 참조
결과
  • 저장 — PNG + Base64로 PlayerPrefs에 보관해 게임을 다시 켜도 닉네임 유지
  • 전송 — 업로드는 접속당 1회, 씬 · 술래 전환 시에도 재업로드 없음
  • 재사용 — 표시하는 UI가 늘어나도 닉네임 이미지는 추가로 전송하지 않음
관련 코드PixelNicknameService.csNicknameRegistry.csPlayerBase.csUIPixelNicknameSetting.cs

TROUBLESHOOTING

쿨타임을 지켰는데 무시되던 물총 발사

술래가 쿨타임(1.5초)에 맞춰 물총을 쐈는데도 간헐적으로 발사가 무시되는 현상이 있었습니다. 클라이언트 입장에선 규칙을 지켰는데 결과가 사라지니, 플레이어가 가장 크게 체감하는 종류의 버그였습니다.

원인 분석
  • 자동 사격으로 현상을 재현하고 서버의 발사 거부 로그를 확인
  • 클라이언트는 1.5초 간격으로 보냈지만, 네트워크 지연 편차로 서버 도착 간격이 기존 허용 기준(1.40초)보다 짧아지는 경우가 있었음
  • 재충전을 TargetRpc로 따로 알려 클라 1발 · 서버 0발처럼 탄약 판정이 어긋나는 경우도 확인
SERVER COOLDOWN CORRECTION
CLIENT
1.5초 간격 발사
SERVER

해결 포인트내용
허용 오차 0.10 → 0.25s도착 간격 ≥ 쿨타임 1.50s − 허용 오차 0.25s 이면 승인. 지연 편차로 짧아진 간격도 정상 발사로 인정
판정 기준 시각 보정다음 기준 = max(도착 시각, 이전 기준 + 1.50s) — 허용 오차를 연달아 써도 연사 속도는 빨라지지 않음
탄약 판정 일치서버도 ServerTick()에서 클라와 같은 주기로 탄약 회복. 재충전 TargetRpc를 제거해 불일치 제거
서버 발사 판정 SeekerWaterGun.cs
private const float ServerCooldownGrace = 0.25f;   // 0.1 → 0.25

[Command]
private void CmdFireWaterGun(Vector2 targetPoint)
{
    // 지연 편차를 감안해 '쿨타임 - 허용 오차' 이상이면 승인
    if (Time.time - _lastServerFireTime < fireCooldown - ServerCooldownGrace)
        return;
    ...
    // 기준 시각은 '이전 기준 + 쿨타임'보다 앞당겨지지 않음 → 연사 속도 유지
    _lastServerFireTime = Mathf.Max(Time.time, _lastServerFireTime + fireCooldown);
    ...
}
결과
  • 발사 — 쿨타임을 지킨 발사는 지연 편차가 있어도 거부되지 않음
  • 공정성 — 허용 오차를 넓혀도 연사 속도는 쿨타임 1.5초 그대로
  • 확장 — 같은 판정을 크로마(Runner) 도발 쿨타임에도 적용
