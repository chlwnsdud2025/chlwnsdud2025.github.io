PROJECT OVERVIEW

3D 인게임에서 수백 마리의 몬스터를, 프레임 저하 없이

뱀서라이크 장르의 재미는 화면을 가득 채운 적을 한꺼번에 쓸어버리는 데서 나옵니다. 하지만 3D에서 적이 수백 마리를 넘어가면 개별 Update, 생성 · 파괴, Animator, 적끼리의 겹침 처리 비용이 한꺼번에 프레임을 끌어내립니다.

4인 팀으로 4주 동안 개발하면서 저는 Enemy · Boss · 맵 · 인게임 흐름을 맡았습니다. Profiler로 병목을 찾고, 같은 조건에서 전후를 비교하며 단계적으로 최적화했고, 웨이브부터 최종 보스까지 이어지는 런 구조를 팀원이 코드 수정 없이 조정할 수 있는 데이터로 설계했습니다.

THE GAME

쏟아지는 몬스터를 쓸어 담고, 장애물과 보스를 넘어

캐릭터를 골라 시작하면 사방에서 몬스터 웨이브가 몰려옵니다. 자동 · 획득 무기로 적을 처치하고, 떨어진 경험치로 레벨업할 때마다 무기와 패시브를 골라 강해집니다. 페이즈를 버티고 나면 회전 발판과 이동 장애물로 가득한 장애물 스테이지, 그리고 보스가 기다립니다.

SURVIVE

웨이브 서바이벌

페이즈마다 정해진 시간 동안 여러 종류의 적 웨이브가 몰려옵니다. 시간 안에 페이즈를 넘기지 못하면 더 거센 악몽 웨이브가 시작됩니다.

GROW

무기 · 패시브 성장

적이 떨어뜨린 경험치 구슬을 모아 레벨업할 때마다 보상으로 무기와 패시브를 골라 나만의 빌드를 만듭니다.

OBSTACLE

장애물 스테이지

전투 사이사이에 회전 발판 · 이동 장애물 · 단차가 있는 액션 구간을 돌파해야 다음으로 넘어갈 수 있습니다.

BOSS

중간 보스와 최종 보스

벌 · 화산 · 팬텀 · 전갈 · 거미 · 쌍둥이 등 보스마다 고유 패턴이 있고, 여섯 번째 페이즈 뒤 포탈을 지나 최종 보스와 싸웁니다.

1-1. 통합 업데이트 — ManagedUpdate

문제 → 판단

Unity가 수백 마리 Enemy의 Update()를 개별 호출해 개체 수만큼 호출 진입점이 늘어났습니다(프레임당 평균 965회). 하나의 루프에서 순회하며 실행하는 구조가 필요하다고 판단했습니다.

결과

EnemyManager의 중앙 루프 하나가 활성 Enemy를 갱신합니다. 개별 Update() 호출 965회 → 0회, BehaviourUpdate 중앙값 7.17 → 6.45ms (−10%).

활성 Enemy를 하나의 루프에서 갱신 EnemyManager.cs

gridUpdateTimer += dt;

for (int i = activeEnemies.Count - 1; i >= 0; i--)

1-2. 오브젝트 풀링

문제 → 적용

수백 마리 Enemy의 생성과 파괴가 반복되면서 Instantiate / Destroy 비용과 GC 스파이크가 지속적으로 발생했습니다. 적의 생명주기(스폰 · 피격 · 사망)에서 생기는 Enemy · 데미지 텍스트 · 경험치 구슬 · 코인 4종을 대기 풀과 활성 객체의 재사용 순환으로 바꿨습니다.

결과

1,000마리 유지 · 30초 측정에서 지속적으로 튀던 GC 할당이 사라지고, 처음 풀을 채울 때만 할당한 뒤 이후 할당 0을 유지합니다. 각 풀의 프리팹 · 크기 · 예비 상한은 EnemyPoolDataSO로 조정합니다.

1-3. VAT + GPU Instancing

문제 → 판단

수백 마리의 SkinnedMeshRenderer · Animator가 동시에 갱신되면서 본 갱신과 개별 드로우 제출 비용이 쌓였습니다. 애니메이션 계산을 CPU에서 GPU로 옮기고, 같은 메시를 인스턴싱으로 묶어야 한다고 판단했습니다.

  4. 셰이더가 시간으로 텍스처 프레임을 샘플링 → 동일 Mesh · Material에 GPU Instancing

1-4. Grid 공간 분할 — 적끼리 겹치지 않게, 싸게

문제 → 판단

적끼리 겹치지 않게 하려고 Unity 물리 충돌을 쓰면 충돌 계산과 물리 콜백 비용이 누적됩니다. 그렇다고 모든 적을 서로 비교하면 비교 횟수가 N²으로 늘어납니다. Rigidbody 없이 충돌과 자연스러운 분산을 구현할 방법이 필요했습니다.

동작 순서
  1. 0.15초마다 활성 Enemy의 월드 위치를 2m Grid 셀 좌표로 바꿔 재등록
  2. 기준 Enemy의 현재 위치로 기준 셀 결정
  3. 기준 셀과 인접 8칸(3×3)에 등록된 후보만 순회
  4. 분리 반경 1.5m 안의 이웃을 최대 5마리 확인해 반대 방향 힘을 이동에 합산

02

NavMesh 없이, 겹쳐 있는 층을 구분해 추적하기

같은 XZ 좌표에 여러 층이 겹치는 지형에서 Enemy가 어느 층으로 가야 하는지 판단하지 못하는 문제를, 수평 이동과 높이 보정을 분리해 해결했습니다.

문제

다층 구조 맵에서 수백 마리가 NavMesh로 경로를 계산하면 비용이 과도하게 발생합니다. 그렇다고 XZ로만 플레이어를 따라가면, 플레이어가 다른 층에 있거나 계단 · 단차를 만났을 때 지면 높이를 맞출 수 없었습니다.

설계

XZ는 플레이어를 직접 추적하고, 높이(Y)만 0.1초마다 이동 예측 위치에서 Raycast로 보정합니다. 플레이어와의 높이 차가 2m 이상이면 다른 층으로 판단합니다. 높이 차가 0.5m를 넘으면 수평 이동을 멈추고 천천히 오르고(Slow Climb), 작은 단차는 빠르게 넘으며(Fast Step), 아래층으로는 낙하합니다.

레이사용 조건동작
Low Ray · Raycast플레이어가 같은 층 (기본 경로 · 비용 최소)예측 위치의 발 위 2m에서 아래로 4m 발사 → 히트하면 그 바닥 높이 유지, MISS(절벽 · 큰 단차)면 High Ray로 재탐색
High Ray · RaycastNonAlloc플레이어가 2m 이상 위층에 있거나 Low Ray가 MISS플레이어 Y + 5m에서 아래로 100m 발사 → 관통한 모든 층의 바닥 히트 중 플레이어 Y와 가장 가까운 층을 목표로 선택
UP

플레이어가 위층

높이 차 ≥ 2m → High Ray → 관통 히트 중 플레이어 Y에 가장 가까운 2층 선택 → 목표 높이까지 Slow Climb.

DOWN

플레이어가 아래층

Low Ray가 발밑 바닥을 못 찾음(MISS) → High Ray fallback → 1층 선택 → 낙하.

SAME

같은 층

Low Ray가 발밑 바닥을 맞힘 → 현재 층 유지. High Ray를 쓰지 않아 비용이 가장 낮은 경로입니다.

High Ray — 관통한 바닥 중 플레이어 높이와 가장 가까운 층 Enemy.cs
int hitCount = Physics.RaycastNonAlloc(highRayStart, Vector3.down, hitBuffer, raycastDistance, groundLayer);
float closestDiff = float.MaxValue;
for (int i = 0; i < hitCount; i++)
{
    float diff = Mathf.Abs(hitBuffer[i].point.y - playerTarget.position.y);
    if (diff < closestDiff)
    {
        closestDiff = diff;
        cachedTargetHeight = hitBuffer[i].point.y;
        cachedHitGround = true;
    }
}

// 높이 차가 0.5m를 넘으면 수평 이동을 멈추고 천천히 오름, 그 외에는 빠르게 단차를 넘음
float currentClimbSpeed;
if (heightDiff > 0.5f) { horizontalVelocity = Vector3.zero; currentClimbSpeed = slowClimbSpeed; }
else currentClimbSpeed = fastStepSpeed;

03

일반 적과 보스, 다른 생명주기를 위한 두 개의 기반 클래스

IDamageable을 공통 계약으로 유지하고, 대량 처리가 중요한 일반 Enemy와 복합 패턴이 중요한 Boss의 책임에 맞게 기반 클래스를 나눴습니다.

구분Enemy (일반 6종)BossEnemy (보스 9종)
대상수백 마리 일반 Enemy의 효율적인 관리소수 Boss의 고유 공격 패턴 관리
갱신ManagedUpdate에서 활성 개체를 일괄 갱신각 Boss가 독립 Update와 Coroutine으로 패턴 실행
확장virtual 메서드로 필요한 동작만 선택적으로 재정의abstract Attack() 구현을 모든 Boss 클래스에 강제
사망Object Pool로 반환사망 이벤트 발행 후 오브젝트 제거
하위 타입Basic · Dash · Range · Laser · Flying · SuicideBee · Volcano · Phantom · Scorpion · Spider · Twin(Geezer · Queen) · 중간 보스 · Final

왜 BossEnemy가 Enemy를 상속하지 않나요? — 일반 Enemy는 중앙 루프 · 풀링 · Grid 분리 계산에 묶여 있는 반면, 보스는 한두 마리가 각자의 코루틴으로 긴 패턴을 실행합니다. 갱신 방식과 생명주기가 다르기 때문에 상속 대신 IDamageable이라는 공통 계약만 공유하게 했습니다. 두 계열 모두 이동 · 피격 · 사망과 공격 진입점은 상위 클래스가 관리하고, 하위 클래스는 필요한 이동 방식과 공격 동작만 재정의 · 추가합니다.

웨이브부터 최종 보스까지, 데이터로 짜는 런 구조

시간 제한 페이즈 → 장애물 스테이지 클리어 → 중간 보스 → 다음 페이즈를 6회 반복한 뒤 포탈을 통해 최종 보스전으로 전환되는 흐름을 ScriptableObject 데이터와 커스텀 인스펙터로 구성했습니다.

데이터역할
Theme · StageTheme_SO테마에서 쓸 Enemy 풀 목록과 페이즈 7개(0~6)를 순서대로 보유
Phase · StagePhase_SO제한 시간 + 정상 웨이브 목록 / 시간 초과 시 악몽 웨이브 목록
Wave · WaveEnemy_DataSO시작 시각 · 간격 · 마리 수 · 적 구성(풀 + 가중치 %) · 미니보스
Enemy · EnemyPoolDataSO프리팹 · 풀 크기 · 예비 상한
진행 루프
  • StageRunManager가 페이즈 진행, 장애물 스테이지, 중간 보스, 포탈과 최종 보스 전환을 관리
  • 제한 시간이 지나면 별도 악몽 타이머와 웨이브를 시작해 후반 압박을 만듦
  • 여섯 번째 페이즈 뒤 포탈을 통해 최종 보스 필드로 전환
Theme SO 커스텀 인스펙터
  • 페이즈 구성 막대 — 제한 시간 비율로 P1~P7 구간 분할
  • 정상 / Nightmare 웨이브 칸을 시작 시각 순으로 배치한 타임라인
  • 웨이브 표 — 시작 · 지속 · 간격 · 마리 · 마리/초 · 보스 · 적 구성(풀 색 + 가중치 %)
  • 행 클릭으로 웨이브 에셋 핑, Ctrl+클릭으로 해당 SO로 바로 이동

팀원 작업 편의 — 웨이브 수치와 적 구성이 코드가 아니라 에셋에 있기 때문에, 기획 · 밸런스 담당 팀원이 코드를 수정하지 않고 인스펙터에서 웨이브와 패턴을 조정할 수 있습니다. 커스텀 인스펙터는 수십 개의 웨이브 에셋을 일일이 열어 보지 않아도 한 페이즈의 흐름을 한눈에 확인하도록 만든 도구입니다.

MEASURE

측정 → 원인 → 적용 → 재측정

Profiler와 Profile Analyzer로 같은 조건의 전후를 비교하며, 감이 아니라 수치로 최적화 효과를 확인하는 방식으로 작업했습니다. 덕분에 효과가 작은 최적화(ManagedUpdate −10%)와 결정적인 최적화(Grid −97.8%)를 구분해 설명할 수 있었습니다.
